# Maintenance and funding plan

The first deliverable is a working version-pinned release transition lab.
A grant request should fund the continued usefulness of this public good.

## First pilot

Publish the code and both genuine evidence runs under the MIT license.
Ask a release tester and a wallet integration developer to repeat and assess
the work. Incorporate feedback before asserting that the project fills an
unmet need. A request for a reference should follow actual review or use.

The applicant should personally repeat the commands, explain the observed
PSBT format transition and understand the wallet-state checks. Public Bitcoin
Core comments must be written by the human contributor in their own words.

## Three month scope

| Month | Deliverable | Acceptance evidence |
| --- | --- | --- |
| 1 | Improve installation and evidence output based on the pilot; map selected 32.0 guide contracts to scenarios | Independent rerun and documented reviewer feedback |
| 2 | Add selected normal workflows requested by downstream users; assess another supported version transition | Version-pinned evidence and at least one downstream integration assessment |
| 3 | Maintain contracts through the next release update and publish a contributor guide | Repeatable release output, resolved feedback and a progress report |

Broader platform support should be introduced only with real runs on each
claimed platform. The first version is Linux x86_64; no other platform has been
validated. Hardware-wallet and external application coverage require separate
fixtures and reviewed scopes.

## Public usefulness

Track independent executions, concrete feedback, requested workflows and
downstream assessments. Publishing more passing reports alone does not prove
added ecosystem value. Use the feedback to choose what to maintain next.
